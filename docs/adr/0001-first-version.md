# Первая версия

Первая версия реализует [требования заказчика](../../customer-requirements.md). Этот ADR объединяет решения о проектах и GitHub-доступах, учётных записях и подготовке окружения локальным агентом.

## Учётные записи и вход

Сотрудник входит в платформу по рабочей почте и одноразовому коду из письма, а затем привязывает личный GitHub-аккаунт для выдачи доступа к репозиториям. Учётная запись платформы самостоятельна; GitHub подключается к ней отдельно. Вход через GitHub как единственный способ входа отклонён.

### Приглашения и первый администратор

Регистрация доступна по одноразовому приглашению на конкретную рабочую почту с ограниченным сроком действия. Администратор может отменить приглашение или выдать новое. Получатель подтверждает указанную почту кодом; одного владения ссылкой недостаточно.

Почта первого администратора задаётся при первоначальной настройке. Он подтверждает её кодом; после создания первой административной учётной записи этот способ создания учётных записей закрывается. Следующих сотрудников и администраторов приглашает действующий администратор.

### Привязка GitHub

Привязка требует подтвердить владение аккаунтом через авторизацию GitHub. Один GitHub-аккаунт соответствует одной учётной записи сотрудника; одновременно привязать его к двум сотрудникам нельзя. Привязка хранится по постоянному GitHub ID и сохраняется при смене логина.

При смене GitHub-аккаунта сначала подтверждается владение новым, затем отзываются доступы старого. Выдача доступов новому начинается только после подтверждённого отзыва у старого. Учётная запись платформы сохраняется; при сбое смена остаётся явно незавершённой.

### Подключение агента

При подключении Codex к MCP сотрудник подтверждает доступ в браузере через вход в платформу. Привязка GitHub-аккаунта для подключения агента не требуется. Агент действует от имени сотрудника, сервер проверяет его актуальные права при каждом запросе. Отключение сотрудника блокирует новые запросы независимо от ранее выданного разрешения.

## Проекты и доступы

Первая версия работает для одной компании и должна закрывать сотруднику доступ к платформе и подключённым репозиториям при его уходе. Поэтому платформа отвечает за все пути доступа сотрудника к этим репозиториям, включая доступы, выданные ранее вне платформы. Управление только выданными платформой доступами упростило бы интеграцию, но оставило бы сотруднику доступ через другие назначения в GitHub.

### Источник решений о доступе

Назначения доступа к проектам задаются в платформе. Проект представляет продукт или бизнес-задачу компании; доступ назначается на проект целиком, без отдельных разрешений на репозитории внутри него. Права в GitHub сами по себе не разрешают проекты в платформе. Изменения напрямую в GitHub считаются расхождениями: платформа автоматически убирает лишние доступы и восстанавливает недостающие по своим назначениям; администратор видит результат исправления.

Сотрудники и их агенты работают от личных GitHub-аккаунтов. Общие аккаунты и deploy keys им не выдаются. Если сотруднику уже известен общий ключ, администратор отзывает или заменяет его до подключения репозитория.

В первой версии есть две роли: администратор и сотрудник. Администратор управляет приглашениями, проектами, инструкциями, интеграциями и назначениями доступа. Сотрудник использует доступные проекты и подключает своего агента.

Администратор видит настройки, инструкции и отчёты всех проектов. Для работы с репозиториями самому и через агента он явно назначает себе проекты на общих основаниях; роль администратора платформы не выдаёт этот доступ автоматически.

### Границы GitHub-интеграции

Административная интеграция использует GitHub App, установленное в организации уполномоченным администратором GitHub. Приложение получает список репозиториев и сведения о них для выбора администратором, а также собственные разрешения для управления доступами. Сотрудник привязывает личный GitHub-аккаунт к учётной записи платформы. Для работы с кодом сотрудники используют личную GitHub-аутентификацию.

Первая версия подключает одну управляемую компанией GitHub-организацию и приватные репозитории. Базовый доступ участников ко всем репозиториям организации отключён. Внешнее управление членством через корпоративный каталог пользователей и enterprise teams не поддерживается.

Для управляемого сотрудника роль владельца GitHub-организации должна быть снята заранее. Такой аккаунт подключается к обычному сценарию только после передачи владения и снятия роли `owner`.

Один репозиторий может входить в несколько проектов. Доступы сотрудника складываются: снятие с одного проекта сохраняет доступ к сведениям о репозитории и права в GitHub, если он разрешён через другой назначенный проект. Обычный сотрудник получает единый уровень `write` ко всем репозиториям назначенных проектов без права администрирования репозиториев. Платформа не ослабляет существующие защиты веток. Отдельного уровня только для чтения в первой версии нет.

### Управление проектами

Платформа создаёт проекты и связывает их с уже существующими GitHub-репозиториями. Создание самих репозиториев, генерация кода по шаблонам и запуск новых сервисов с нуля в первую версию не входят.

Администратор может создавать, изменять и архивировать проекты. При архивировании проект убирается из доступных сотрудникам и агентам, а выданные через него права в GitHub отзываются. Доступ к репозиторию сохраняется, если он разрешён через другой назначенный проект. История и отчёты сохраняются, сами GitHub-репозитории не удаляются.

### Отключение при сбое GitHub

При отключении сотрудника платформа сразу блокирует его доступ и новые запросы агента. Если GitHub недоступен, отзыв доступа к репозиториям остаётся незавершённым и автоматически повторяется до подтверждения результата. Администратор видит незавершённый отзыв и возможность сохранения доступа к репозиториям.

При доступном GitHub цель отзыва доступа составляет не более 5 минут с момента отключения сотрудника. Если через 5 минут отзыв не завершён, в том числе из-за сбоя GitHub, администратор видит просрочку, а платформа продолжает попытки. Истечение срока само по себе не подтверждает отзыв доступа.

### Подключение существующих доступов

До включения автоматического управления платформа показывает администратору существующие доступы и план изменений. Старые права не превращаются автоматически в назначения проектов. Автоматическое управление начинается после принятия плана администратором. Если устранение лишнего доступа затронет неуправляемых пользователей или сторонние репозитории, сначала требуется ручная настройка.

## Агент и подготовка окружения

Для первой версии выбран Codex CLI, который работает на компьютере сотрудника и подключается к удалённому MCP платформы. Платформа выдаёт разрешённые сотруднику проекты, репозитории и инструкции, а агент готовит окружение локально от его имени. Такое разделение оставляет выполнение команд на компьютере сотрудника, а проверку доступа к данным платформы на сервере.

### Инструкция и результат подготовки

Git, Codex CLI, вход в Codex и личная GitHub-аутентификация считаются исходными условиями на компьютере сотрудника. Платформа показывает порядок настройки, сотрудник готовит инструменты и личные входы по инструкции, а агент проверяет их наличие. Автоматическая установка базовых инструментов и оплата моделей от имени компании в первую версию не входят.

Администратор хранит инструкцию подготовки проекта в платформе. Она задаёт порядок подготовки и критерии готовности, а команды и скрипты могут находиться в репозиториях, на которые она ссылается.

Окружение считается готовым после получения всех репозиториев проекта, выполнения инструкции подготовки и успешного прохождения указанных в ней проверок. Одной проверки доступа к GitHub недостаточно; недостающий секрет, который мешает подготовке, не позволяет подтвердить готовность.

Проектные секреты сотрудник получает через существующий в компании порядок и задаёт локально. Платформа не хранит эти секреты и не передаёт их агенту. Инструкция перечисляет необходимые секреты и порядок их получения. При их отсутствии агент сохраняет незавершённый результат с причиной; после ручного шага подготовку можно продолжить.

Платформа сохраняет отчёт агента о проверенных репозиториях, выполненных шагах, результатах проверок и препятствиях к завершению. Отчёт виден сотруднику и администратору. Агент проверяет доступ к коду локально от имени сотрудника. Платформа проверяет доступ к своим сведениям и права в GitHub отдельно от отчёта агента о подготовке.

После изменения инструкции или состава репозиториев прежний отчёт сохраняется как история с указанием прежней версии проекта. Он не подтверждает актуальную готовность: для неё нужны повторная подготовка и проверки по новым требованиям.

### Пользовательский интерфейс

Администратор управляет сотрудниками, проектами, инструкциями и GitHub-подключением через веб-интерфейс. Сотрудник видит назначенные проекты, состояние доступов и порядок подключения агента. Агент получает сведения через MCP.

В первой версии агент может получать разрешённые сотруднику проекты, репозитории и инструкции и отправлять отчёт о подготовке. Управление сотрудниками, проектами, интеграциями и правами выполняется через веб-интерфейс администратора. Локальную подготовку окружения выполняет агент.

MCP используется в первой версии. Платформа проверяет доступ к сведениям и отправке отчётов, но не выдаёт отдельных разрешений на запуск локальных команд. Их выполнение регулируется Codex CLI и его настройками.

## Проверка первой версии

Первую версию проверяем на одном реальном проекте: администратор приглашает сотрудника и назначает проект; сотрудник привязывает GitHub-аккаунт; платформа выдаёт права на репозитории проекта; сотрудник подключает агента; агент получает все репозитории, выполняет инструкцию и проверки, сохраняет отчёт, видимый сотруднику и администратору. При недостающем секрете или неуспешной проверке отчёт указывает причину, а готовность не подтверждается. После отключения сотрудника закрываются доступы к платформе и репозиториям, а агент перестаёт получать новые данные компании. Команды проверок задаются инструкцией конкретного проекта.

Проверяем отзыв всех путей доступа к подключённым репозиториям при отключении сотрудника, включая прежние назначения вне платформы. Также проверяем сохранение доступа через другой назначенный проект и незавершённый отзыв при сбое GitHub.

Конкретный проект для приёмки, его состав и операционная система выбираются позднее и не определяют состав первой версии.
